# 構成の判断記録

`AGENTS.md` と各設定ファイルが「なぜそうなっているか」の記録です。

`AGENTS.md` には運用に必要な指示だけを置き、根拠はこのファイルに分離しています。
**`AGENTS.md` から `@` で import していません。** 毎セッション読み込むとコンテキストを消費し、
指示の遵守率が下がるためです（公式が示す 200 行目安の趣旨）。必要なときに開いてください。

## 凡例

| 印       | 意味                                                                   |
| -------- | ---------------------------------------------------------------------- |
| **公式** | Claude Code 公式ドキュメントに明記があり、それに従った項目。出典を併記 |
| **判断** | 公式に規定がなく、この雛形として選択した項目。変更してよい条件を併記   |

## 記入の作法

設定や指示を変更したら、このファイルの該当行も更新してください。

- **公式** に分類するのは、公式ドキュメントの**原文を読んで確認した**項目だけ。出典 URL を必ず併記する
- **判断** には、理由と「変更してよい条件」を必ず書く。理由のない行は後から判断できないため価値がない
- 確認していない仕様を **公式** に分類しない。確認していなければ **判断** にするか `[曖昧]` を付ける
- 採用しなかった選択肢も「6. 採用を見送った項目」に残す。同じ検討を繰り返さないため

| ディレクトリ一覧・設計理由・フックの仕組みの説明を置かない | **公式** | 同上 Exclude 列 — "Anything Claude can figure out by reading code" "Long explanations or tutorials" "File-by-file descriptions of the codebase" に該当するため削除した |

## 1-b. 応答と作業の進め方

**この節はすべて判断です。** 公式ドキュメントは応答の態度について規定していません。

| 項目                               | 理由 / 変更してよい条件                                                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 既存資産の活用を先に検討する       | このリポジトリの所有者の方針。新規実装は保守対象が増えるため最終手段とする                                                                 |
| 迎合しない・率直に述べる           | 同上。同意できない点を飲み込むと、誤った前提のまま作業が進むため                                                                           |
| 確度の低い情報に `[曖昧]` を付ける | 同上。断定と推測が同じ見た目で並ぶと、受け手が検証すべき箇所を判断できないため                                                             |
| 作業報告は「何をどうしたか」だけ   | 同上。経緯と背景は求められたときに出す                                                                                                     |
| 非エンジニア向けに説明する         | 同上。都度「非エンジニア向けに」と指示させるのは非効率。理解できないまま指示・判断させると作業のミスを生み、開発への悪影響の方が大きいため |

雛形として使うときは、チームの方針に合わせて書き換えてください。`AGENTS.md` の
「応答と作業の進め方」が実体で、この節はその根拠です。

「非エンジニア向けの説明」「常に丁寧な態度と言葉遣い」は一度 AGENTS.md から削除した。理由は
[best-practices](https://code.claude.com/docs/en/best-practices) の判定基準
（"Would removing this cause Claude to make mistakes?"）に照らすと、この2件は間違えると
損害が出る指示ではなく好みの範疇で、同表の Exclude 列 "Self-evident practices" に近いため。
外部評価（AGENTS.md が説明過多という指摘）を受けて、AGENTS.md 全体をこの基準で見直した際に
あわせて削った。

その後「非エンジニア向けの説明」はユーザーの指摘により復活させた。理解できないまま指示や
判断をさせること自体が作業のミスを生むという理由は、上記の判定基準（間違えると損害が出るか）
を満たすため、Exclude ではなく Include 側の判断に改めた。「常に丁寧な態度と言葉遣い」は
この理由に該当しないため削除したままにしている。

## 2. 権限（`.claude/settings.json`）

| 項目                                                                     | 区分     | 根拠 / 理由                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------ | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ルールの記法（`Bash(cmd *)` `Read(./path)` `:*`）                        | **公式** | [permissions](https://code.claude.com/docs/en/permissions)                                                                                                                                                                                           |
| 鍵ファイルに `Edit` deny も付ける                                        | **公式** | 同上 — "NotebookEdit isn't covered, so add an `Edit` deny rule"                                                                                                                                                                                      |
| `Bash(rm *)`（`rm -rf *` ではなく）                                      | **公式** | 同上 — 最初の `*` より前は文字通り一致するため、`rm -fr` を取りこぼす                                                                                                                                                                                |
| `curl`/`wget` を deny し WebFetch に許可を与える                         | **公式** | 同上 — この2つを一組で推奨している                                                                                                                                                                                                                   |
| deny は allow より優先する                                               | **公式** | [permissions](https://code.claude.com/docs/en/permissions) — 評価順は Deny → Ask → Allow                                                                                                                                                             |
| allow / deny に**何を入れるか**の選定                                    | **判断** | 記法は公式、中身は私の選択。使うコマンドに合わせて各プロジェクトで調整してよい                                                                                                                                                                       |
| 読み取り専用の git を allow に入れる                                     | **判断** | `show` `fetch` `branch` `rev-parse` `ls` を許可。破壊的な部分集合（`branch -d`/`-D`）は deny 優先の原則どおり deny 側で個別に塞ぐ                                                                                                                    |
| `git branch -d`/`-D` を deny                                             | **判断** | `Bash(git branch *)` の allow はブランチ削除も含んでしまう。`rm`/`reset --hard` と同じ形で、破壊的な部分だけ deny に足して塞いだ                                                                                                                     |
| `git push` を ask から allow に移す                                      | **判断** | `--force` と `-f` は deny 済みで deny が allow に優先し、`main` 直 push は Ruleset が止める。二重の確認より許可の回数を優先した                                                                                                                      |
| PR 監視系の `mcp__Claude_Code_Remote__*` を allow                        | **判断** | `subscribe`/`unsubscribe`_pr_activity、trigger の作成・更新・削除・即時実行、`send_later` はコードやリポジトリを変更しない。CI 監視のたびに確認を求められていたため追加した                                                                          |
| `WebFetch` を `code.claude.com` に限定                                   | **判断** | この雛形が公式ドキュメントを参照する前提のため。必要なドメインは追加してよい                                                                                                                                                                         |
| `respectGitignore: true`                                                 | **判断** | 公式の分類では「Interface and terminal」であり、セキュリティ設定ではない。害がないので残しているだけ                                                                                                                                                 |
| サンドボックスを既定で有効化**しない**                                   | **判断** | 公式は defense-in-depth として推奨している。ネイティブ Windows で動かず `allowWrite` が環境依存のため、壊れた既定を配らない選択                                                                                                                      |
| `permissions.defaultMode` を書かない                                     | **判断** | プロジェクト値がユーザー値を上書きするため、全員の auto モードを奪う。`"auto"` はプロジェクトファイルからは効かず選択肢が非対称                                                                                                                      |
| `.claude/` 配下は「保護パス」で `permissions.allow` では事前承認できない | **公式** | [permission-modes](https://code.claude.com/docs/en/permission-modes) の Protected paths 節。`Edit(.claude/**)` を allow に入れても効果がなく、毎回確認を求められる。止めるレバーは `bypassPermissions` モードのみ（deny も含め全プロンプトを止める） |

## 3. フック

| 項目                                                                                        | 区分     | 根拠 / 理由                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 指示は助言、フックは決定論的という区別                                                      | **公式** | [best-practices](https://code.claude.com/docs/en/best-practices) — "hooks are deterministic and guarantee the action"                                                                                                                                                                                            |
| フックの JSON 構造・`async`・`additionalContext`                                            | **公式** | [hooks](https://code.claude.com/docs/en/hooks)                                                                                                                                                                                                                                                                   |
| `SessionStart` の `matcher: "startup\|resume"`                                              | **公式** | [cloud-environments](https://code.claude.com/docs/en/cloud-environments) の例。無いと `/clear` のたびに走る                                                                                                                                                                                                      |
| PostToolUse で整形を走らせるという発想                                                      | **公式** | [hooks](https://code.claude.com/docs/en/hooks) に同型の例がある                                                                                                                                                                                                                                                  |
| `format.sh` / `typecheck.sh` の**実装**                                                     | **判断** | `jq` に依存せず `node` で解析、拡張子フィルタ、成功時は無出力。いずれも私が書いた                                                                                                                                                                                                                                |
| 型検査を `check` ではなく `typecheck` にする                                                | **判断** | Vitest の起動分だけ遅くなるため。テストまで走らせたい場合は差し替えてよい                                                                                                                                                                                                                                        |
| 4フックとも `${CLAUDE_PROJECT_DIR}` ではなく標準入力 JSON の `cwd` へ `cd` する             | **公式** | [hooks](https://code.claude.com/docs/en/hooks) の Worktrees 節 — `${CLAUDE_PROJECT_DIR}` は worktree に入っても元のチェックアウトを指したままだが、`cwd` は worktree のパスに追従する。`AGENTS.md` は当初からこの仕様を書いていたが、フックの実装が追いついていなかった（未検証のまま放置していた）              |
| `typecheck.sh` の `node_modules` 存在チェックを cwd 直下だけでなく祖先ディレクトリも辿る    | **判断** | `EnterWorktree` で実際に worktree に入って E2E 検証したところ発覚。worktree には `node_modules` 自体が無いが、`pnpm run typecheck` はディレクトリを上へたどってメインチェックアウトの `node_modules`（tsc）を見つけて解決できる。旧実装は cwd 直下しか見ておらず、worktree では型検査が黙って no-op になっていた |
| `format.sh`/`typecheck.sh`/`handoff-check.sh` の `cwd` 対応は harness 経由の E2E で検証済み | **判断** | `EnterWorktree` で worktree に入り、実際に Edit で `.ts` を編集して PostToolUse を、worktree を dirty にしてターンを終えて Stop を、それぞれ本物の harness 経由で発火させた。`handoff-stamp.sh`（SessionEnd）だけは実際にセッションを終了させないと発火できないため、サンプル JSON の手動テストのみ              |

## 3-b. セッション間の引継ぎ

既存実装3つ（[392fyc/claude-handoff](https://github.com/392fyc/claude-handoff)、
[shihchengwei-lab/claude-code-session-kit](https://github.com/shihchengwei-lab/claude-code-session-kit)、
[who96/claude-code-context-handoff](https://github.com/who96/claude-code-context-handoff)）を調べ、
書き込み側は2つ目の方式を採った。読み込み側は3つとも SessionStart フックを使っているが、
この雛形では**フックではなく `@` import** にした（理由は下表）。

| 項目                                                                                                      | 区分     | 根拠 / 理由                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| import は再帰的に展開される（最大4段）                                                                    | **公式** | [memory](https://code.claude.com/docs/en/memory) — "Imported files can recursively import other files"                                                                                                                                                                                                                                                                                           |
| プロジェクト直下の指示はコンパクション後も再注入される                                                    | **公式** | 同上 — "Project-root CLAUDE.md survives compaction"                                                                                                                                                                                                                                                                                                                                              |
| プロジェクトのフックは workspace trust を要求する                                                         | **公式** | [hooks](https://code.claude.com/docs/en/hooks) — "Project-level hooks follow workspace trust rules"                                                                                                                                                                                                                                                                                              |
| SessionEnd はモデルを呼べず、予算が既定 1.5 秒                                                            | **公式** | 同上 — "SessionEnd hooks share a 1.5-second budget"。timeout を上げると最大 60 秒まで拡張できる                                                                                                                                                                                                                                                                                                  |
| Stop は毎ターン発火し、exit 2 で会話を継続させられる                                                      | **公式** | 同上 — "Stop fires once per turn"、"exit code 2 prevents Claude from stopping"                                                                                                                                                                                                                                                                                                                   |
| 読み込みは SessionStart フックではなく `@` import                                                         | **判断** | フックは trust 承認まで動かず、コンパクション後の再注入もない。import は両方を満たす。あわせて文章でも読むよう指示している（Codex は import を展開しないため）                                                                                                                                                                                                                                   |
| Stop フックで差し戻す                                                                                     | **判断** | session-kit の方式。スキルは必ず発火しないため、確実性が要るならフックしかない                                                                                                                                                                                                                                                                                                                   |
| 引継ぎは `main` へのマージまでを完了とする                                                                | **判断** | コンテナは終了後に破棄され、次のセッションは `main` を新規クローンする。作業ブランチへのコミットだけでは失われるため、マージしない引継ぎは存在しないのと同じ                                                                                                                                                                                                                                     |
| ただしマージ必須の対象は「引継ぎ文」に限る。コード自体は未完了なら push 済み branch/worktree に残してよい | **判断** | 当初は「main へマージするまで完了」と一体で扱っていたが、これは誤りを含んでいた。**push 済みのコミットは origin に残るため消えない**——消えるのは push していないコミットだけ。次セッションが自動で読むのは `main` の `docs/handoff.md` だけなので、必須なのは引継ぎ文が `main` に載ることで、worktree 越しの継続開発（未完了タスクを branch に残し、次セッションが続行する）を妨げるべきではない |
| `/checkin` と `/checkout` をスキルとして用意する                                                          | **判断** | 作業の開始と終了は人が決めるタイミングであり、フックで検出できない。呼び出し口を用意し、手順を固定した                                                                                                                                                                                                                                                                                           |
| 差し戻しは**1セッションに1回だけ**                                                                        | **判断** | Stop は毎ターン発火するため、無条件に止めると作業にならない。マーカーで抑止している                                                                                                                                                                                                                                                                                                              |
| `docs/handoff.md` を**コミット対象**にする                                                                | **判断** | gitignore にするとクラウドセッション（毎回 fresh clone）で必ず失われるため。複数人で編集すると競合しうる点は許容した                                                                                                                                                                                                                                                                             |
| SessionEnd では機械的な事実だけ記録する                                                                   | **判断** | モデルを呼べないため文章は書けない。ブランチ・HEAD・変更ファイルはシェルだけで取れる                                                                                                                                                                                                                                                                                                             |
| `handoff.md` の役割を「今どの branch を見ればいいか」のポインタに絞る。branch 固有の詳細は書かない        | **判断** | 外部評価の指摘。`main` 上の単一ファイルが複数 branch の状態を同時に代表しようとすると、並列 worktree で片方の更新がもう片方を上書きする。branch 固有の詳細はその branch 自身のコミットや PR 本文に置き、`handoff.md` には列挙用の短いポインタだけを置く形にした                                                                                                                                  |
| 「注意点」に恒久的なリポジトリのルールを再掲しない。`AGENTS.md`/`docs/decisions.md` を参照する            | **判断** | 同上の指摘。実例として、当時の「注意点」に `main` 直 push 禁止・CI ジョブ名の制約など、セッションが変わっても変わらない事実が複数混入していた。これらは既に `AGENTS.md`/`docs/decisions.md` にあり、二重管理は食い違いの元になる                                                                                                                                                                 |
| 同時並行の複数 branch を前提にしたタスク管理層（Issue/Task 単位の状態ファイル等）は追加しない             | **判断** | 外部評価は Goal→Issue→Branch→Worktree→Agent の階層構造を提案したが、この雛形の実運用は直列（1セッション=1系統の作業）であり、使うかどうか未確定の機構を配るのは「AGENTS.md の分量削減」で確立した基準（使わない仕組みを配らない）と矛盾する。複数 branch が同時進行する場合は「次にやること」に箇条書きで列挙する軽量な対処に留め、本格的な状態管理が要るなら再検討する                          |
| `handoff-stamp.sh` は追記ではなく上書き                                                                   | **判断** | `<!-- session-end-stamp -->` 以降を毎回まるごと置き換える実装（`text.slice(0, i) + block`）であることをコード上で確認済み。外部評価は「ログが伸び続ける」懸念を挙げたが、この実装では起きない                                                                                                                                                                                                    |

**この仕組みの限界を明記しておく。** 「セッション終了時にモデルへ引継ぎを書かせる」手段は公式に存在しない。
SessionEnd はモデルを呼べず、Stop はターン単位でしか発火しない。したがって確実に得られるのは
「1セッションに1回の差し戻し」と「終了時の機械的な記録」までで、文章の鮮度は保証されない。
区切りごとに `/handoff` を実行するのが最も確実である。

## 4. 技術スタック

**この節はすべて判断です。** Claude Code 公式ドキュメントはスタックについて何も規定していません。

| 項目                                                | 理由 / 変更してよい条件                                                                    |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Node 22 / TypeScript 5 strict / pnpm / ESM / Vitest | 「鉄板構成」として選択。差し替えは自由。指示ファイルの構成は影響を受けない                 |
| `.npmrc` の `engine-strict` と `.node-version`      | Node 界隈の慣行。`engines` を宣言だけで終わらせないための組み合わせ                        |
| `tsconfig.json` / `tsconfig.build.json` の2分割     | テストを型検査の対象に含めつつ `dist/` に出力しないための一般的パターン                    |
| CI ワークフローの内容                               | GitHub Actions の一般知識。公式の Claude 用 Actions とは別物（後述のとおり同梱していない） |
| ジョブ名を汎用の `check` にする                     | 実行内容が増減しても陳腐化しないため。改名時は Ruleset の必須チェックも同時に更新すること  |

## 9. 失敗行動台帳・放置台帳

**この節はすべて判断です。** Anthropic/OpenAI の公式ドキュメントが定めた仕様ではありません。
ユーザーが提示した外部研究資料（arXiv の Graph Engineering 論文、NASA Systems Engineering、
Shape Up 等を扱った調査レポート）を踏まえてユーザーと合意した設計です。当の論文自身も
Graph Engineering を「まだ確立していない新興概念（emerging paradigm）」と位置づけており、
公式ベストプラクティスではないことに注意してください。

| 項目                                                                                | 理由 / 変更してよい条件                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `docs/failure-action-log.md` を作る。書きっぱなしでよい                             | 失敗のたびに整理を判断させるとその判断自体の仕組みが要る。書く側の負担をゼロにし、整理コストは読む側（`failure-reviewer`）に寄せた                                                                               |
| 結果ではなく行動を書く                                                              | 結果（バグ・CI赤など）は `docs/test-policy.md` とテスト・CIの担当領域であり、同じものを書くと二重管理になる。テストでは捕まらない「AIの判断・手順のクセ」を残すのがこの台帳の役割                                |
| 失敗したと気づいた、その場で本人が書く                                              | 最終的な解決を待つと、行き詰まったまま終わったセッションでは何も記録が残らない。一番使いたい場面（行き詰まっているとき）で台帳が空になるのを避けた                                                               |
| 正解ではなく、確実な失敗行動を除外するために読む                                    | 台帳には正解は書かれていない。しかし「これは確実に失敗する」と分かっている行動は減らせる。選択肢を絞る消去法としての価値であり、答えを教える機能ではない                                                         |
| 通常のセッションでは読まない                                                        | コンテキストを圧迫するため。読むのはユーザーの明示的指示、または行き詰まって何が悪いか分からないときだけ                                                                                                         |
| 読む前に必ずユーザーへ確認する                                                      | AI がサブエージェントを自分の判断だけで呼び出せると、呼び出し基準が曖昧なまま暴走しうる。ユーザーの承認を必須にした                                                                                              |
| `failure-reviewer` は今の状況に一致する記録を探し、無ければ「該当なし」と報告する   | 一致しない記録を代わりに提示すると、無関係な情報に基づいて判断させてしまう。見つからないことも正直に報告させる                                                                                                   |
| `failure-reviewer` は正解・戦略を提案しない                                         | 「失敗行動を報告する役割」と「それを踏まえて次にどう動くか判断する役割」を分離した。後者は呼び出し元（本編のAI）の役割                                                                                           |
| `docs/neglected-log.md` を作る。ゴール到達時のみ読む                                | 放置したままゴールできたなら致命的ではなかったことの裏付けになる一方、ゴール定義自体が最初から完全ではないため、放置事項に未知の重大リスクが紛れる可能性がある。リリース前に一度だけ棚卸しする安全弁として置いた |
| `docs/test-policy.md` の Backlog Rule も `docs/neglected-log.md` へ統合             | 両者とも「放置してもゴールできる」性質の記録で、記録先を分ける理由がない。分けたままだとAIが毎回どちらに書くか迷う。ユーザーの指示で統合した                                                                     |
| 書くきっかけを「Gateに触れたが破らなかった（ヒヤリハット）」に限定                  | 書く・書かないの基準を「放置しても次に進めるか」で統一。Gateを突き破ったものは即座に直すため放置できない。触れてもいないものは記録する価値がない。ユーザーの提案（ガードレールの比喩）をそのまま採用             |
| 書く内容を「日時・触れたGate・対象箇所」の3点に限定し、理由は書かせない             | 理由を書かせると読み手が「その理由が正しいか」を推測で判断することになり、test-policy.mdのEvidence Rule（証拠なき`たぶん`の禁止）と矛盾する。「いつ・どこ」だけを渡し、読み手が実際に確認しに行く設計にした      |
| ゴールは大計画に対して1つ。「問題がなければ即リリースできる状態」だけをゴールと呼ぶ | ユーザーの明示的な定義。Node／branch 単位の部分完了をゴールと呼ばない                                                                                                                                            |
| 台帳2ファイルに `.gitattributes` で `merge=union` を設定                            | 複数 branch が並行して同じファイルの末尾に追記する運用のため、素の3-way mergeでもコンフリクトは起きにくいが、両者の追記を確実に両方残すため明示した                                                              |
| `failure-reviewer` サブエージェントを追加                                           | 「1. 指示ファイルの構成」で一度見送った「サブエージェントを空にする」方針を、この機能に限り撤回した。中身のないサンプルではなく、失敗行動台帳の整理という具体的な必要から追加した                                |

#### 敵対的検証（3視点AI）で見つかった、実装前に対処が必要な4つの欠陥

上記の設計案そのものを、技術的／業務フロー／リスクの3視点で敵対的に検証したところ、
複数の視点が独立に指摘した重大な欠陥が4つ見つかった。**これらを解決してから実装すること。**

1. **計画ファイルの並列編集問題**（技術的視点＋リスク視点が指摘）。複数AIが同時に「全体進捗」や
   依存先フェーズ番号を書き換えると、更新が消えたりズレた依存参照が残ったりする。これは
   `docs/handoff.md`で一度指摘・修正した「単一ファイルが並列worktreeと両立しない」問題の再発
2. **再採番で過去の参照が壊れる**（技術的視点＋リスク視点が指摘）。フェーズ分割（ステップ10以上）
   や計画見直し（寄り道9超過）が起きると、既存の番号（失敗行動台帳・放置台帳・PR・コミットが
   引用している番号）との対応が壊れる。番号は不変という前提と、動的に分裂しうる設計が矛盾
3. **計画者＝実行者＝完了判定者が同一AI**（リスク視点＋業務フロー視点が指摘）。敵対的検証は
   「依存関係の申請」だけが対象で、「本当に完了したか」「これは本当に寄り道か」という自己申告
   部分は誰も検証していない。数字操作（ステップを細かく刻んで進捗を良く見せる等）を防ぐ仕組みが
   構造的にない
4. **「寄り道の定義を決めない」ことが抜け道になる**（業務フロー視点＋リスク視点が指摘）。AIを
   型にはめない工夫だったが、同時に「何が寄り道かをAI自身が決められる」抜け道でもある。本体の
   進捗を止めたくないAIが、問題を寄り道側に逃がすインセンティブが生まれうる

単独の視点からの指摘（優先度は下がるが記録しておく）: 分母固定がフェーズ分割時に「後退した
ように見える」逆効果を生みうる（業務フロー視点）／"Task Graph"と称する割に依存関係を機械的に
追跡する実体（グラフ構造）がない、ラベルにすぎない（技術的視点）／敵対的検証の結果を読む
強制チェックポイントがなく形骸化しうる（技術的視点＋リスク視点）／表示が「一点だけ見たい」
というユーザーの要求と裏腹に4階層の数字が並び情報過多（業務フロー視点）。

次回セッションは、上記4つの欠陥への対処案をユーザーと詰めてから実装に進むこと。

#### 一次情報の調査結果（2026-08-30）

「4つの欠陥を個別に潰すのではなく、計画の立て方／立てるタイミング／全体計画とセッション実行
計画の境界／セッション粒度を先に確定すれば解決できるのではないか」というユーザーの指摘を受け、
一次情報（公式ドキュメント・公式リポジトリ）を調査した。3系統が同じ3層構造に収束していた。

| 層           | Anthropic 長時間エージェント        | GitHub spec-kit                         | 性質                   |
| ------------ | ----------------------------------- | --------------------------------------- | ---------------------- |
| 動かない     | （CLAUDE.md 相当）                  | `constitution.md`（不変の原則）         | 恒久ルール             |
| 長生きする   | `feature_list.json`                 | `spec.md`（"the primary artifact"）     | 全体計画。書き換えない |
| 毎回作り直す | 各セッションが未完の最優先を1つ選ぶ | `plan.md` / `tasks.md`（"Regenerable"） | 実行計画。使い捨て     |

主な原文根拠:

- **計画は一度だけ作る**: 初期化専用エージェントが機能要件ファイルを一度書く。形式は JSON
  （"the model is less likely to inappropriately change or overwrite JSON files compared to
  Markdown files"）。実行側は `passes` フラグの真偽値だけを変える。
  出典: Anthropic「Effective harnesses for long-running agents」
- **セッション粒度は「1回に1機能」**: 一括実装（one-shot）でコンテキストが尽きる失敗を経て
  "work on only one feature at a time. This incremental approach turned out to be critical."
  1単位の大きさは end-to-end の検証手順を書ける大きさ。同上
- **セッションをまたいで残すのは4つ**: 進捗ファイル／説明的な git コミット履歴／完了フラグ付き
  機能リスト／環境復元スクリプト。"compaction doesn't always pass perfectly clear instructions
  to the next agent" として自動圧縮任せを明確に否定。同上
- **番号は不変・追記のみ**: 既存タスクIDの最大値 M を求め `T{M+1:03d}` から採番。既存タスクの
  書き換えは MUST NOT。残作業ゼロなら "byte-for-byte unchanged"。
  出典: GitHub spec-kit `/speckit.converge`
- **並列可否は計画時に静的判定**: `[P]` マーカーは "different files, no dependencies" のときだけ
  付ける。禁止事項に "same file conflicts" が明記。出典: spec-kit `tasks-template.md`
- **完了判定は作業者から分離**: "a verification subagent ... so the agent doing the work isn't
  the one grading it"。証拠（テスト出力・実行コマンドと戻り値・スクリーンショット）を出させる。
  出典: Claude Code 公式ベストプラクティス。spec-kit `/speckit.converge` は git 履歴もチェック印も
  見ずコード実体だけを見る（"no git, no branch comparison, no history"）
- **観測された自己申告の失敗**: 「進んでいるのを見て勝手に完了宣言する」「十分にテストせず完了
  マークを付ける」「ユニットテストや curl は通るが end-to-end では動いていないことに気づかない」。
  出典: Anthropic 長時間エージェント記事
- **計画が不要な下限**: "If you could describe the diff in one sentence, skip the plan."
  出典: Claude Code 公式ベストプラクティス
- Claude Code の Plan mode は計画の保存先を公式に規定していない（＝セッション内限りの道具）。
  セッションをまたいで残る公式の仕組みは `CLAUDE.md` / auto memory (`MEMORY.md`, 先頭200行または
  25KB) / `/goal` の3つ。サブエージェントは親の会話履歴・読んだファイル・auto memory を一切
  引き継がない（fork を除く）

#### 上記を踏まえた設計変更案（未合意・ユーザー確認待ち）

4つの欠陥への対処:

| 欠陥             | 対処                                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------------------- |
| ① 並列編集       | 計画ファイルへの書き込みを「末尾への追記」と「自分の担当項目の状態1箇所」だけに制限。全体進捗は誰も書かず数えて導出 |
| ② 再採番         | 番号は不変。分割・追加は最大値+1で末尾に追記。「ステップ10以上で新フェーズに分割」を廃止                            |
| ③ 自己申告       | 完了判定を、状態欄も git 履歴も見ないまっさらな別AIに委譲。「確かめ方」の手順を実際になぞらせ、証拠を出させる       |
| ④ 寄り道の抜け道 | 寄り道枠を廃止。計画外作業は末尾に番号付きで追記する（逃がす先がなくなる）                                          |

元の設計から捨てることになるもの:

1. 4階層の番号体系（ライン→フェーズ→ステップ→寄り道）→ 2階層（項目番号のみ、不変・連番）へ。
   ラインは番号から外し、並列可否マーカーという属性にする
2. フェーズの動的分割（ステップ10以上）→ 廃止
3. 寄り道枠（最大9）→ 廃止
4. 「依存関係テストのみで分割、ファイル重複は基準にしない」→ 公式はファイル重複も並列判定に
   入れている（spec-kit の "same file conflicts"）。要再検討
5. 分母の事前固定 → 追記で分母は増える。ただし「当初計画 X/Y」「追加分 A/B」を分けて表示すれば
   当初計画分は後退しない

維持するもの: グラフエンジニアリング方式、担当を番号から分離、依存関係を文章で明記して非エンジニア
が確認できるようにする、3視点の敵対的検証、コードブロックで番号を固定する。

計画ファイルの具体的な書式案（会社紹介サイトを題材にした例）:

```
T001  [並列可]  トップページの骨組み
      できるもの : ヘッダー・本文枠・フッターが並んだHTML 1枚
      確かめ方   : ブラウザで開く → 画面幅をスマホ相当まで狭める
                   → 文字が画面からはみ出していないこと
      依存       : なし
      触るファイル: index.html
      状態       : 済
```

「確かめ方」は人間が画面でたどれる手順で書く（「テストが通る」ではなく「押す・見る」）。
これを書けない項目は、粒度が大きすぎるというシグナルになる。

#### 未解決のまま残る点

- **複数AIが同時に同じ計画ファイルを触るときの排他制御は、どの一次情報にもない `[曖昧]`。**
  spec-kit は「別ファイルのタスクだけ並列可」にしてそもそも競合させない方向で回避しており、
  ロック機構を持たない。書き込みを追記のみに制限すれば実害はほぼ消えるが、確認はできていない
- 全体計画のファイル形式を JSON（書き換えにくいが非エンジニアに読みにくい）にするか、Markdown の
  コードブロック（読みやすいが書き換えられやすい）にするか
- 完了判定を `/checkout` に組み込むか、独立したサブエージェントにするか
- 1つの全体計画に項目をいくつ置くか（Anthropic の実例は200項目以上）

#### 検証の層構造（2026-08-30 の続き。未実装・未合意）

「完了判定を別 AI にやらせる」を `/checkout` に置くと**そのセッションで作った 1 項目しか
見ない**、では 100 項目の検証リストはいつ使うのか、というユーザーの指摘から整理した。
検証には性質の異なる 3 つの場面があり、これを混同していた。

| いつ           | 何を検証するか                     | 誰が                  | コスト   |
| -------------- | ---------------------------------- | --------------------- | -------- |
| セッション終了 | 今回やった 1 項目だけ              | まっさらな別 AI       | 小・毎回 |
| セッション開始 | 前回までの成果が今も動くか、ざっと | 着手する AI 自身      | 小・毎回 |
| 全体照合       | 全項目                             | 別 AI（書き込み不可） | 大・節目 |

**全体照合が必要な理由はデグレ検出。** ある項目を「済」にした後、別の項目の作業でそれが
壊れても、セッション単位の検証は構造的に検出できない（「済」の項目はもう誰も見に行かない
ため）。全体照合は「状態」欄も git 履歴も見ず、コード実体だけを「確かめ方」と突き合わせる。
**公式**：spec-kit `/speckit.converge` は「does not track changes ... no git, no branch
comparison, no history」、仕様を「the sole source of intent」として現在のコードと照合し、
missing / partial / contradicts / unrequested に分類する。書き込みは末尾追記のみ。

**CI が緑でも意味がない場合への公式の対処は「単一チェックの精度を上げる」ではなく
「性質の違う層を重ねる」。** Claude Code 公式は検証を強度順に 4 段階で並べており、最上位は
「a fresh model try to refute the result, so the agent doing the work isn't the one
grading it」（まっさらなモデルに反証させる）。1〜3 は「決めた手順が通るか」を見るのに対し、
4 は「間違っているのでは」を能動的に探す点で性質が違う。失敗パターンには
「The trust-then-verify gap」という名前が付いており、対処は
「If you can't verify it, don't ship it.」。

**見えない範囲は潰さず記録する。** Anthropic は Puppeteer 経由でブラウザ標準の警告ダイアログ
が見えないことを把握していたが、検証ツールを改良せず「it can't see ... features relying on
these modals tended to be buggier as a result」と書き残しただけだった。調査システムでも
ルーブリックによる LLM 採点をすり抜けた問題（SEO 最適化された内容の薄い情報源を選ぶ傾向）を
最終的に捕まえたのは人間のテスターだった。**このリポジトリの放置台帳・失敗行動台帳と同じ
発想であり、整合する。**

対処案：全体計画の各項目に「自動化」欄を持たせ、CI で確認できるものと人間が確認するしかない
ものを区別する。人間が見るのは後者だけで済み、「CI が緑でも誰も見ていない項目」が一目で分かる。

**注意点**：反証させる別 AI には副作用がある。公式が明記している——「A reviewer prompted to
find gaps will usually report some, even when the work is sound」。対策は
「flag only gaps that affect correctness or the stated requirements」。既存の
`failure-reviewer` サブエージェントを「正解・戦略は提案しない」と縛っているのと同じ発想。

**新たに増えた未決の点**：

- 「自動化」欄を 2 段階（CI / 人間）にするか、間に「別 AI が画面操作で確認できる」を挟んで
  3 段階にするか
- 全体照合を 10 項目ごとに走らせるか、大計画のゴール到達時だけにするか
- 全体照合で壊れが見つかったとき、既存項目を「済」から「未」に戻す（進捗が後退する）か、
  新番号で末尾に追記する（進捗は後退しないが同じものが 2 箇所に載る）か

#### 非エンジニアが確認する場合の設計（2026-08-30 の続き。未実装・未合意）

「AI は信用できない、CI は見ない、人間は非エンジニア。誰が検証するのか」というユーザーの
指摘から整理した。**前提を1つ逆転させることで解ける。**

**非エンジニアはボトルネックではなく、唯一の正解保持者。** 会社概要ページの本社住所が
引っ越し前のままでも、料金表が ¥3,000 のところ ¥300 でも、**AI も CI も永久に気づかない**。
人間だけが「何が正しいか」を知っている。これは非エンジニアが最も得意な検出であり、
同時に最も価値の高い検出でもある。

**したがって聞き方を変える。人間には「これで合っていますか」しか聞かない。
「このコードは正しいですか」は絶対に聞かない。** 後者は確認ではなく責任の押し付けで、
非エンジニアは「はい」と答えるしかなく検証として機能しない。

聞き方の要件は3つ:

- **証拠はスクリーンショット・実物にする。ログやテスト出力は人間に見せない。**
  **公式**：「Have Claude show evidence rather than asserting success: ... or a screenshot
  of the result」「do all testing as a human user would」
- **選択肢つきの質問にする**（例:「受信箱に届いていますか？ はい／いいえ／届いたが内容が
  おかしい」）。専門知識ゼロで確実に答えられる形にする
- **人間が見るのは「自動化」欄が★の項目だけ。** 100 項目中 5 件程度に絞る

**「AI を信用しない」の実装は「疑う」ではなく「証拠を出させる」。** 疑うのは人間の労力を
食うので非エンジニアには続かない。証拠を出させれば労力は AI 側に寄る。人間に届く前に、
作った本人でない別 AI が反証して大半を落とす。

**CI は人間が見なくてよい。** 緑でも赤でも人間の行動は変わらない（赤なら AI が直すまで
待つだけ）。CI は人間向けではなく、AI が自分の仕事を確かめるための道具である。

**それでも 3 層をすり抜ける失敗が残る**（今は動くが作りが脆い／セキュリティ的に危ない）。
AI は自作なので気づきにくく、CI は「今動くか」しか見ず、非エンジニアには構造上見えない。
**公式にもこれへの答えはない `[曖昧]`**（Anthropic は専門エージェントへの分業で改善しうるが
未確定と明記して止めている）。対処は「潰す」ではなく「受け入れたと記録する」——
既存の `docs/neglected-log.md`（放置台帳）がこの役割を果たし、ゴール到達時に読む。
Anthropic が Puppeteer の盲点を直さず書き残したのと同じ扱い。

**新たに増えた未決の点**：★の項目を人間に聞くタイミングを、溜めて一括（10 項目ごと、または
ゴール到達時）にするか、出たらすぐにするか。溜めても確認待ちの項目は「未」のまま止まるので
進捗の数字は嘘にならない。

なお「自動化」欄は **2 段階（CI で確認できる／人間が確認するしかない）で確定**。3 段階目
（別 AI が画面操作で確認できる）は項目の性質ではなく作業の進み具合を表すため採らない。

#### ユーザーが確定させた点（2026-08-30）

議論の結果、次の 4 点が確定した。**これ以外はまだ未決であり、実装には入っていない。**

| 項目                        | 決定                                                                                               | 理由                                                                                                                         |
| --------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 全体計画のファイル形式      | **JSON**                                                                                           | **公式**：Anthropic「the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files」 |
| 「自動化」欄                | **2 段階**（CI で確認できる／人間が確認するしかない）                                              | 3 段階目（別 AI が画面操作で確認できる）は項目の性質ではなく作業の進み具合を表すため                                         |
| ★項目を人間に聞くタイミング | **溜めて一括**                                                                                     | ★は元々少ない。1 件ずつ呼ぶと続かない。溜めても確認待ち項目は「未」のまま止まるので進捗の数字は嘘にならない                  |
| 3 層構造と番号の扱い        | 恒久ルール／全体計画（不変・追記のみ）／使い捨ての実行計画。番号は不変、追加は最大値 +1 で末尾追記 | **公式**：Anthropic と spec-kit が独立に同じ構造へ収束。spec-kit `/converge`「既存タスクの書き換えは MUST NOT」              |

（人間が見るのは★項目の確認画面と進捗の数字だけで、計画ファイル本体は AI が読む）。
この点は実装時に必ず確認する。

#### 残っていた 5 点も確定（2026-08-30）

ユーザーが AI 側の推奨をすべて採用した。**これで設計上の未決はなくなり、実装に入れる状態。**

| 項目                     | 決定                                                                     | 理由                                                                                                                                                                         |
| ------------------------ | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 完了判定の置き場所       | **独立したサブエージェントを作り `/checkout` から呼ぶ**                  | `/checkout` に直接書くと「早く終わらせたい」文脈と同居する。既存の `failure-reviewer` と同じ形にできる                                                                       |
| 並列可否の判定基準       | **ファイルの重複も入れる**（既存の合意を変更）                           | worktree で隔離しても `main` へのマージ時に衝突する。**公式**：spec-kit は `[P]` の条件を「different files, no dependencies」とし、禁止事項に「same file conflicts」を挙げる |
| 全体計画の項目数         | **数を先に決めない。「1 項目＝1 セッションで終わる大きさ」を基準にする** | 数を先に決めると粒度をそれに合わせて歪める動機が生まれる。目安は初回 30〜50（Anthropic の実例 200 以上はアプリ 1 本を丸ごと作る規模）                                        |

| 全体照合で壊れが出たとき | **「済」は戻さず、末尾に新番号で追記**                                   | 番号不変の原則と一貫する。「済」を「未」に戻すと同じ項目が 2 回「済」になり履歴が壊れる。追記なら「一度完成し、後で直した」事実がそのまま残る                                |

#### 実装時に持ち越す注意点

- **JSON をそのまま人間に読ませない。** 人間が見るのは★項目の確認画面と進捗の数字だけ
- **人間への質問は選択肢つきの YES/NO にする。** 証拠はスクリーンショットや実物で示し、
  ログやテスト出力は見せない。「このコードは正しいですか」は聞かない
- **完了判定サブエージェントには範囲を縛る指示を入れる。** **公式**が警告している——
  「A reviewer prompted to find gaps will usually report some, even when the work is sound」。
  対策は「flag only gaps that affect correctness or the stated requirements」。
  既存の `failure-reviewer` を「正解・戦略は提案しない」と縛っているのと同じ発想
- **複数 AI が同じ計画ファイルを同時に触るときの排他制御は一次情報になく `[曖昧]` のまま。**
  書き込みを「末尾追記」と「自分の担当項目の完了フラグ 1 個」に限定することで実害はほぼ消える
  想定だが、確認はできていない

### 10. 全体計画（`docs/plan.json`）の実装

設計は「9. 失敗行動台帳・放置台帳」内「保留にした部分：Task Graph」以下に記録した確定 9 点に
従った。ここには**実装で下した追加の判断**だけを書く。

| 判断                                                   | 理由                                                                                                                                                                    |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 検証を `src/plan.ts` の関数として書き CI で回す        | 「番号は不変・追記のみ」は人間の注意力では守れない。id の昇順チェックは、既存項目を書き換えたことの検出を兼ねる。**自動化できるものは CI へ**という自分たちの方針の実践 |
| 並列可否をフィールドに持たず `canRunInParallel` で導出 | `dependsOn` と `files` から決まる値を別に持つと、両者が食い違う。導出なら矛盾しようがない                                                                               |
| 進捗もフィールドに持たず `countProgress` で導出        | 複数 AI が同時に合計値を書き換えると競合する（欠陥①）。数えれば必ず正しい                                                                                               |
| `status` に `awaiting_human` を設けた                  | 「AI 側は終わったが人間の確認待ち」を `done` と区別する。溜めて一括で聞く（確定事項）ために必要で、かつ確認待ちを完了に数えないので進捗の数字が嘘にならない             |
| `origin` に `initial` / `added` を持たせた             | 追記で分母が増えても「当初計画 3/8」が後退しない。3 視点検証で出た「分母固定が後退に見える」という指摘への対処                                                          |
| `verify` と `files` を空にできない制約                 | 確かめ方を書けない項目は粒度が大きすぎる。触るファイルが分からない項目は並列可否を判定できない。どちらも空欄を許すと設計全体が空洞化する                                |
| 検証は最初の違反で打ち切らず全件返す                   | 書いた人が一度に全部直せるようにするため                                                                                                                                |
| 実際の `docs/plan.json` は雛形に含めない               | 雛形の時点では中身が決められない。`docs/plan.example.json` を見本として置き、テストは実ファイルが存在するときだけ検証する（`describe.skipIf`）                          |

**追加したファイル**：`src/plan.ts` / `src/plan.test.ts` / `src/plan.file.test.ts` /
`docs/plan.example.json` / `.claude/agents/completion-checker.md` /
`.claude/skills/plan-init` / `.claude/skills/plan-verify` / `.claude/skills/plan-ask`。
`/checkin` に「次の1項目を選ぶ」、`/checkout` に「完了判定を受ける」を追加した。

**`AGENTS.md` に「全体計画」節を追加した理由**：`.claude/` 配下は Codex から見えない。
サブエージェントとスキルに閉じた運用ルールは Codex が守れないため、正本を `AGENTS.md` に置く。

**残る `[曖昧]`**：複数 AI が同時に `docs/plan.json` を編集するときの排他制御。書き込みを
「末尾追記」と「自分の担当項目の `status` 1 個」に限定したことで実害はほぼ消える想定だが、

**未検証の懸念を `AGENTS.md` に直接書いた理由**：別台帳を作らない、というユーザーの判断。
台帳を増やすと読むきっかけの設計（いつ読むか、誰が読むか）が新たに必要になるうえ、
この懸念は「全体計画を使うたびに目に入るべきもの」で、`AGENTS.md` は毎セッション読まれる。

`T006` の `verify` の2つ目は「実際に1項目で試し、`/goal` が正しく『満たした』と判定することを
確認する」。**これは AI のセッションからは原理的に実行できない。** `/goal` は人がターミナルに
入力するコマンドで、メインのセッションからもサブエージェントからも起動できない。

判定役（`completion-checker`）に最終判定を求めた結果は「**通らなかった**」。その理由の要点:

- 手順1（`AGENTS.md` に手順がある）は満たされている
- 手順2は「やってみたら失敗した」のではなく「**そもそも実行できない**」
- deliverable の文面（手順が書かれている状態）だけを見れば満たされているが、
  **`verify` は deliverable の言い換えではなく、より強い要求**。手順2を落として
  deliverable だけで合格にするのは、判定基準を後から緩めること

| 分かったこと                                  | 内容                                                                                                                                                                     |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`automation` の分類が実態と食い違っていた** | `T006` は `ci`（機械で確認できる）になっているが、手順2は人の操作を要する。**`human` が正しかった**                                                                      |
| なぜ間違えたか                                | `/plan-init` の分類基準は「その手順を機械が実行できるかどうか」。`/goal` は Claude Code の機能なので機械側だと考えたが、**起動できるのは人だけ**だった                   |
| 「未検証の懸念」が現実になった                | `AGENTS.md` に書いていた「`verify` を人間がたどれる手順として書き続けられるか `[曖昧]`」——**崩れ方は「書けなくなる」ではなく「書けているが AI には実行できない」だった** |
| 直せないこと                                  | `docs/plan.json` の既存項目は書き換え禁止のため、`automation` を `human` に直すことはできない。**この節が記録**                                                          |

**次に同じことを防ぐには**: `automation` を決めるとき、「機械が実行できるか」を
**そのコマンドを誰が入力するか**まで下りて確かめる。「Claude Code の機能だから機械側」は
