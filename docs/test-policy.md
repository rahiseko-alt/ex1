# テスト方針（重大度ゲート）

このファイルは、テストで見つかった問題をどの順番で・どこまで直すかを決めるための
**判定手順**です。Claude Code と Codex のどちらがテストを実行しても、同じ手順で同じ
結論に至ることを目的としています。読み手がどの AI エージェントであっても、本文の
記述だけで再現できるように書いてあります。解釈の余地を残さないため、要約せず
全文をそのまま使ってください。

## 対象と非対象

- **対象**: テスト・レビュー・手動確認で見つかった不具合や懸念点を、直すべきか・
  後回しにしてよいかを判定する場面
- **非対象**: コミット前に必ず通す `pnpm run check` / `pnpm run build`
  （`AGENTS.md` の「Git 運用」節で別途必須と定めている）。あれは「今回の変更が
  仕様どおり動くか」の確認であり、このファイルは「見つかった問題にどう対処するか」
  の判定です。両者は独立しており、どちらも省略できません

## 根拠

このファイルの構成（重大度順のゲート判定、証拠なき YES の禁止、下位問題の先送り）
は、ISTQB のリスクベーステスト、ISO/IEC/IEEE 29119、OWASP Risk Rating Methodology、
一般的な Quality Gate / Exit Criteria の考え方を、個人開発・AI エージェント運用向けに
翻案したものです。公式の1標準そのものではありません。詳細な照合結果は
`docs/decisions.md` の「7. テスト方針（test-policy.md）」を参照してください。

---

## 目的

テストで発見した問題を重大度順に処理し、重要でない問題への過剰修正・過剰検証・無限ループを防止する。

テストでは必ず本チェックリストを上から順番に判定する。
1つでも NO が出た時点で停止する。
NO より下位の項目は、その時点では調査・修正・議論しない。
修正後は再度 No.001 から判定する。

## 実行規則

1. No.001 から順番に YES / NO で判定する。
2. UNKNOWN は NO として扱う。
3. 最初に NO になった項目だけを今回の修正対象とする。
4. 下位項目の問題を先回りして修正してはいけない。
5. 修正後は No.001 から再実行する。
6. 上位項目を壊す可能性がある修正は禁止する。
7. テストのためだけの不要な本番コード追加は禁止する。
8. 「念のため」「将来起こるかもしれない」は修正理由にしない。
9. 実際に再現できない問題は原則として修正対象にしない。
10. 明示された要求を超える改善を勝手に行わない。
11. リファクタリングはテスト修正と混ぜない。
12. 既存仕様を変更してテストを通してはいけない。
13. テストを削除・弱体化して通してはいけない。
14. 問題の重大度を AI 自身の感覚で変更してはいけない。
15. このリストの順序が優先順位そのものである。

## 判定方法

各項目について以下だけを出力する。

```text
001 YES
002 YES
003 NO
STOP
```

NO の場合は続けて以下を出力する。

```text
FAILED_GATE: 003
EVIDENCE:
原因:
修正対象:
修正しない範囲:
検証方法:
```

長い説明は禁止。

## Priority Test Gate

各項目は「3桁のゼロ埋め ID」で管理する。`判定方法`・`Release Gate`・`Scope Rule` 等の
参照は全てこの ID を指す。Markdown の自動リスト整形で番号がずれないよう、コードブロックで
固定してある。

### P0 — 絶対停止領域

```text
001 実行によって人命・身体・重大な安全上の危険を発生させないか？
002 認証・認可を回避して、本来アクセスできない情報や機能へアクセスできないか？
003 他ユーザー・他顧客・他テナントのデータへアクセスできないか？
004 秘密鍵、APIキー、パスワード、アクセストークン等の秘密情報が漏洩しないか？
005 本番データを意図せず削除・破壊・上書きしないか？
006 復旧不能なデータ破損を発生させないか？
007 支払い・請求・送金等で誤った金額処理を行わないか？
008 権限のないユーザーが管理者操作を実行できないか？
009 ユーザーAの操作がユーザーBの状態を不正に変更しないか？
010 本番環境全体を停止させる既知の不具合がないか？
```

### P1 — 製品成立条件

```text
011 今回の実装は明示された目的を満たしているか？
012 必須要件がすべて実装されているか？
013 主要ユースケースが開始から完了まで成立するか？
014 ユーザーが最も重要な目的を達成できるか？
015 主要機能が実行不能になっていないか？
016 正常系の主要フローが途中で停止しないか？
017 入力した主要データが正しく保存されるか？
018 保存した主要データを正しく取得できるか？
019 主要な更新操作が正しく反映されるか？
020 主要な削除操作が仕様どおり動作するか？
```

### P1 — データ整合性

```text
021 必須データが欠落しないか？
022 データ型が破壊されないか？
023 ID・ユーザー・顧客等の関連付けが正しいか？
024 重複してはいけないデータが重複生成されないか？
025 1回の操作が意図せず複数回実行されないか？
026 更新途中の失敗によって不整合状態が残らないか？
027 失敗した処理を成功として記録しないか？
028 成功した処理を失敗として扱わないか？
029 日時・タイムゾーン処理が主要仕様を壊していないか？
030 数値計算・丸め・集計結果が主要仕様どおりか？
```

### P1 — セキュリティ基本

```text
031 ユーザー入力によって任意コード・SQL・コマンド等を実行できないか？
032 XSS等により任意スクリプトを実行できないか？
033 外部入力を信用しすぎて重要処理を実行していないか？
034 認証済みユーザーの識別が正しく行われているか？
035 ログアウト・セッション失効後に保護された操作を実行できないか？
036 URLやIDの変更だけで他人のリソースを参照できないか？
037 重要なサーバー側判定をクライアント側だけに依存していないか？
038 秘密情報をログへ平文出力していないか？
039 エラーメッセージから内部秘密情報が露出しないか？
040 依存サービスの失敗時に危険なデフォルト動作をしないか？
```

### P2 — 主要障害耐性

```text
041 主要APIが失敗した際にアプリ全体が破綻しないか？
042 通信タイムアウト時に無限待機しないか？
043 再試行によって同じ処理を重複実行しないか？
044 外部サービス停止時にデータを破壊しないか？
045 不正入力によってアプリ全体がクラッシュしないか？
046 null / undefined / 空値等で主要処理が停止しないか？
047 存在しないリソース参照時に適切に失敗できるか？
048 部分的失敗を全成功として扱わないか？
049 途中キャンセル時に危険な中間状態を残さないか？
050 同時操作によって主要データが破壊されないか？
```

### P2 — 主要UX

```text
051 ユーザーが主要操作を完了できるUIになっているか？
052 主要ボタン・入力欄・リンクが操作可能か？
053 主要画面が表示不能になっていないか？
054 成功・失敗がユーザーに判別できるか？
055 処理中であることが必要な場面で判別できるか？
056 入力エラー時にユーザーが修正可能か？
057 必須入力項目が仕様どおり扱われているか？
058 主要画面遷移が正しいか？
059 戻る・再読み込み等の一般操作で主要処理が破壊されないか？
060 スマートフォン利用が主要要件の場合、主要操作が成立するか？
```

### P2 — API・連携

```text
061 外部APIへ仕様どおりの値を送っているか？
062 外部APIからの主要レスポンスを正しく解釈しているか？
063 APIエラーを成功として扱っていないか？
064 Webhook等の重複受信で二重処理しないか？
065 外部サービス認証失効を適切に処理できるか？
066 外部サービスのレスポンス変更で即座に危険動作をしないか？
067 外部サービスへ不要な秘密情報を送信していないか？
068 連携先を間違えて本番データを送信しないか？
069 dev / staging / production の接続先を誤っていないか？
070 外部連携の失敗が主要データの整合性を壊さないか？
```

### P3 — 回帰

```text
071 今回の変更前に正常だった主要機能を壊していないか？
072 変更したモジュールの直接利用箇所が正常か？
073 変更したAPIを利用する主要画面が正常か？
074 変更したDBスキーマを利用する主要機能が正常か？
075 既存ユーザーのデータで主要処理が成立するか？
076 既存設定を維持したまま動作するか？
077 既存URL・主要導線を不用意に破壊していないか？
078 既存APIの必須互換性を破壊していないか？
079 設定変更によって別環境を壊していないか？
080 今回の変更範囲に対する主要回帰テストが通るか？
```

### P3 — 性能・運用

```text
081 通常利用で主要操作が実用不能なほど遅くないか？
082 明らかな無限ループがないか？
083 明らかな無限再試行がないか？
084 通常操作で異常な量のAPI呼び出しを発生させないか？
085 通常操作で異常な量のDBアクセスを発生させないか？
086 通常利用でメモリ・CPU等を異常消費しないか？
087 ログが異常増殖し続けないか？
088 障害原因を追跡する最低限のログが存在するか？
089 主要な失敗を運用者が検知可能か？
090 バックアップ・復旧が要件の場合、その最低条件を満たしているか？
```

### P4 — 低優先度品質

```text
091 明らかに誤解を招く文言がないか？
092 主要レイアウトが著しく崩れていないか？
093 通常利用で頻繁に発生する軽微な操作不良がないか？
094 主要ブラウザ・主要端末要件を満たしているか？
095 アクセシビリティ要件として明示された項目を満たしているか？
096 不要な警告・エラーが大量発生していないか？
097 明らかなデッドコード・重複処理が今回の変更によって障害原因になっていないか？
098 今回変更したコードが最低限理解・保守可能な状態か？
099 今回の要件に必要なドキュメント更新が完了しているか？
100 今回の要求範囲内に、再現可能で実害のある未解決問題が残っていないか？
```

## Release Gate

通常の小規模個人開発では以下を基準とする。

**必須**

```text
001〜080 = ALL YES
```

ここに NO が1件でもあればリリース不可。

**条件付き許容**

```text
081〜090
```

実運用上問題になるものだけ修正する。
理論上の性能問題や、現在の利用規模では発生しない問題は修正不要。

**原則リリース阻害要因にしない**

```text
091〜100
```

明示要件・高頻度の実害・顧客影響がある場合のみ修正する。
単なる改善余地はバックログへ送る。

## 修正禁止ルール

以下を理由に修正を開始してはいけない。

```text
・コードをもっと綺麗にできる
・将来使うかもしれない
・理論上は問題が起きる可能性がある
・100%安全ではない
・ベストプラクティスではない
・もっと汎用化できる
・もっと抽象化できる
・もっと高速化できる
・テストカバレッジを100%にできる
・別アーキテクチャの方が美しい
・AIが気になる
```

これらは今回の要求ではない限り無視する。

## Backlog Rule

081〜100 で発見した問題のうち、今回修正しないものは `docs/neglected-log.md` へ以下の形式で
記録する（日時は同ファイルの必須ルールに従う）。

```text
ID:
問題:
実害:
発生条件:
優先度:
対応: BACKLOG / IGNORE
```

記録後は作業を続けない。

## Scope Rule

テスト中に別問題を発見しても、その問題が現在の FAILED_GATE より下位の場合は修正しない。

例:

```text
現在:
023 NO

同時に発見:
087 NO
094 NO
```

この場合に修正するのは 023 だけ。
087 と 094 は記録のみ。

## Test Selection Rule

すべてのテストを毎回実行する必要はない。
ただし、Gate 判定に必要な証拠は取得する。
優先順位は以下。

```text
1. 既存自動テスト
2. 変更箇所の自動テスト
3. 型チェック / lint / build
4. API・DB 等の統合テスト
5. 主要 E2E
6. 手動確認
```

目的はテスト数を増やすことではない。
各 Gate を YES と判定できる証拠を得ること。

## Evidence Rule

YES 判定には根拠が必要。

許可される根拠:

```text
・自動テスト成功
・型チェック成功
・build成功
・実際のAPIレスポンス
・DB状態確認
・E2E成功
・再現手順による確認
・仕様との照合
```

以下は禁止。

```text
・たぶん
・コードを見る限り
・問題なさそう
・一般的には
・理論上
・おそらく
```

確認できない場合は UNKNOWN = NO とする。

## Test Creation Rule

新しいテストを書くのは以下の場合のみ。

1. 今回修正したバグの再発防止に必要。
2. 主要要件を検証する既存テストがない。
3. 同じ不具合が再発する現実的可能性がある。

以下の場合は書かない。

```text
・カバレッジ率を上げるだけ
・極端なedge case
・現実には到達不能な状態
・内部実装を固定するテスト
・単純なライブラリ動作の再テスト
```

## Edge Case Rule

Edge Case は以下の順で扱う。

```text
1. 実際に発生した
2. ユーザー操作で容易に発生する
3. 外部入力により現実的に発生する
4. 発生確率は低いが損害が重大
5. 理論上のみ存在する
```

1〜4 は必要に応じて対応する。
5 は原則無視する。

## Completion Rule

以下を満たしたらテスト工程を終了する。

```text
001〜080 ALL YES
かつ
今回の必須要件 ALL PASS
かつ
新しいP0/P1問題なし
```

081〜100 に未解決問題があっても、Release Gate を満たしているなら終了してよい。
AI は追加改善を提案して作業を延長してはいけない。

## Final Output

完了時は以下だけを報告する。

```text
TEST RESULT: PASS

Gate:
001-080: PASS

Optional:
081-090: PASS / OPEN
091-100: PASS / OPEN

Release blockers: 0

Unresolved:
- 必要なら記載

Decision:
RELEASE READY
```

失敗時:

```text
TEST RESULT: FAIL

FAILED_GATE: XXX
原因:
証拠:
修正対象:
修正しない範囲:

Decision:
STOP
```

## 最重要原則

```text
上から判定する。
最初のNOで止まる。
そのNOだけ直す。
直したら最初からやる。
下位問題を先回りして直さない。
080を超えた問題で開発を無限化させない。
```

テストの目的は「問題をゼロにすること」ではない。
リリースを阻害する重要な問題をゼロにすることである。
