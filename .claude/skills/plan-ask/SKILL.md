# 確認をまとめて聞く

**人間に聞いてよいのは「これで合っていますか」だけです。**

## なぜ人間に聞くのか

AI と CI には、原理的に見えないものがあります。

```
会社概要ページに、本社住所が「東京都◯◯区 1-2-3」と表示されている。

  AI  : 正しく表示されている。問題なし
  CI  : テスト通過。緑
  人間: 「そこ、去年引っ越した。今は違う住所」
```

**AI も CI も、これには永久に気づきません。** 料金が ¥3,000 のところ ¥300 でも同じです。
人間は検証の穴を埋める補助ではなく、**何が正しいかを唯一知っている人**です。

## いつ使うか

`status` が `awaiting_human` の項目が溜まったとき。1件ずつ呼び出さないでください。
★は元々少ないので、1件ごとに呼ぶと相手が続きません。溜めても、確認待ちの項目は
`awaiting_human` のまま完了に数えないので、進捗の数字が嘘になることはありません。

## 手順

### 1. 溜まっている項目を集める

`docs/plan.json` から `status` が `awaiting_human` の項目を全て取り出します。

### 2. 聞く前に、AI 側の準備を終えておく

人間に「確認してください」と言う前に、**確認できる状態を作っておきます。**
テストメールを実際に送る、画面を実際に開ける状態にする、など。
準備せずに聞くのは、作業を押し付けているだけです。

### 3. 1件ずつ、選択肢つきで聞く

```
確認をお願いします（3件）

────────────────────────────────
1/3  問い合わせフォームの送信先

  やったこと : あなたのアドレス宛にテストメールを1通送りました
  見てほしい : 受信箱（迷惑メールフォルダも）
  質問       : 届いていますか？

  [ はい ]  [ いいえ ]  [ 届いたが内容がおかしい ]
────────────────────────────────
2/3  会社概要の中身

  やったこと : 打ち合わせでいただいた資料のとおりに入力しました
  見てほしい : http://localhost:3000/about.html
  質問       : 社名・住所・設立年は合っていますか？

  [ 合っている ]  [ 違うところがある ]
────────────────────────────────
```

**証拠は実物で示します。** スクリーンショット、実際の画面、届いたメール。
ログやテスト出力は見せないでください。

### 4. 答えを反映する

- 「はい」→ その項目の `status` を `done` にする
- 「いいえ」「おかしい」→ `status` は `awaiting_human` のまま。何がどう違うかを聞き、
  末尾に新しい番号で直しの項目を追記する

## 聞いてはいけないこと

**これは確認ではなく、責任の押し付けです。**

```
✗  T009 の実装が完了しました。nodemailer で SMTP 経由の送信処理を実装し、
   エラーハンドリングも追加しました。テストも通っています。確認をお願いします。
```

相手は「はい」と言うしかありません。何も検証されていません。

- **「このコードは正しいですか」と聞かない**
- **専門用語で状況を説明しない**（ライブラリ名、実装方式、テストの通過は相手の判断材料にならない）
- **YES/NO で答えられない聞き方をしない**
- **一度に全部並べて「確認してください」と丸投げしない**（1件ずつ、番号を振って聞く）
