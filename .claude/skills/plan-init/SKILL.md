# 全体計画をつくる

**このスキルは1つのプロジェクトにつき1回しか使いません。** すでに `docs/plan.json` が
あるなら、実行せずにその旨を報告して終わってください。計画を作り直すことは、
過去の番号への参照を全て壊すことを意味します。

## なぜ一度だけなのか

長時間の作業は、記憶が消える細切れのセッションに分かれます。毎回のセッションは
「前のシフトの記憶がないまま出勤してくる交代要員」のようなものです。**全員が同じものを
見て動くために、計画は動かない土台である必要があります。**

だから計画に対してできることは2つだけです。

- 各項目の `status` を変える
- **末尾に**新しい項目を追記する（番号は既存の最大値 +1）

既存の項目を書き換える・削除する・番号を振り直すことは**してはいけません。**

## 手順

### 1. ゴールを1文で決める

「問題がなければ即リリースできる状態」を書きます。ユーザーに確認してください。

### 2. 項目に分ける

**数を先に決めないでください。** 1項目の大きさは次で決まります。

> **1項目 = 1セッションで終わる大きさ = end-to-end の確かめ方を書ける大きさ**

一気に全部やろうとするとコンテキストが尽きて失敗します。逆に、差分を一文で説明できる
ほど小さいものは項目にする必要がありません。目安は初回で30〜50項目です。

**確かめ方が書けない項目は、粒度が大きすぎます。** 分けてください。

### 3. 各項目を JSON で書く

`docs/plan.example.json` と同じ形にします。項目ごとに次を埋めます。

| 欄            | 書くこと                                                             |
| ------------- | -------------------------------------------------------------------- |
| `id`          | `T001` から連番。一度振ったら不変                                    |
| `title`       | 一言の名前                                                           |
| `deliverable` | 完成すると何ができるか。依存する側がこれを読んで判断できるように書く |
| `verify`      | 確かめ方。**人間が画面でたどれる操作の手順**として書く               |
| `dependsOn`   | 依存する項目の id                                                    |
| `files`       | 触るファイル。**重複を隠さず全て挙げる**（並列可否の判定に使う）     |
| `automation`  | `ci`（自動で確かめられる）か `human`（人間が実物を見るしかない）     |
| `status`      | 最初は全て `todo`                                                    |
| `origin`      | 最初に作った項目は全て `initial`                                     |

**`verify` の書き方が最も重要です。**

```
✗  「テストが通る」「正しく動作する」「エラーが出ない」
✓  「トップページの『会社概要』を押す」「戻るボタンでトップに戻れる」
✓  「自分宛に1通送る」「受信箱に届いていることを確認する」
```

**この書き方は機械で検査されます。** `docs/plan.json` を保存して `pnpm run test` を実行すると、
下の2つの条件を満たさない項目があるだけで検証が落ち、どの項目のどの手順が悪いかが出ます
（検査しているのは `src/plan.ts` の `validateVerifySteps`）。

- **手順1つは、前後の空白を除いて8文字以上**。それより短いものは、何をどうすると何が
  起きるかを書けていないとみなして弾きます
- **その項目の確かめ方のどこかに「確認」「確かめ」「説明してもらう」のどれかの言葉が
  入っていること**。何をもって「できた」と判断するかを示す語です。1手順ずつではなく
  項目ごとに見ます（「index.html を開く」のような下ごしらえの手順に期待結果が無いのは
  当然のため、そこまで求めると正しい書き方まで弾いてしまう）

条件を満たすためだけに言葉を足しても意味がありません。検査は書き方の下限を見ているだけで、
**その手順を人間が本当にたどれるかどうかは機械には分かりません。**

**`automation` の判定基準**：その手順を機械が実行できるかどうかだけで決めます。
「まだテストを書いていない」は `human` の理由になりません（それは作業の進み具合であって、
項目の性質ではない）。実際の受信箱、印刷結果、ブラウザ標準の警告ダイアログのように
**機械から見えないもの**だけが `human` です。

### 4. 検証を通す

```bash
pnpm run test
```

`docs/plan.json` があると自動で検証されます。id の重複・順序、確かめ方の空欄、
存在しない依存先などがここで弾かれます。

### 5. ユーザーに見せる

**JSON をそのまま見せないでください。** 次の形に直して確認をとります。

```
ゴール: 会社の紹介サイトが公開でき、問い合わせが届く状態

  T001  トップページの骨組み
        できるもの: ヘッダー・本文枠・フッターが並んだHTML 1枚
        確かめ方  : 開く → 幅を375pxまで狭める → 文字がはみ出していない
        依存      : なし

  ...（全項目）

  人間が確認するしかない項目: 3件（T005, T012, T028）
```

聞くのは「**この順番と分け方で合っていますか**」だけです。
「この設計は妥当ですか」とは聞かないでください。
